# 开发计划

> **本文件夹是什么**：项目按版本推进的唯一入口。现有可运行工程已经作为基线入库；之后按「先写清下一刀，再动手」推进，只为最近的一两个小版本写全套细化。
>
> **本文件夹不是什么**：不是把现有脚本重写成另一套架构的任务清单。代码长什么样以 `Assets/Scripts/` 为准。做完的版本记在 [`../更新日志/更新日志.md`](../更新日志/更新日志.md)。

## 1. 版本号约定

两段式 `主.次`，只用这两段，不做补丁号。

| 版本段 | 含义 |
| --- | --- |
| **现状** | 已入库的第三人称动作游戏基线 |
| **0.x** | `fix`。行为向本就该有的结果收敛。0.1–0.36 已完成，号不改。大纲见 [`Ver 0.x/README.md`](Ver%200.x/README.md) |
| **1.x** | `refactor`、`optimize`。可观察结果不变。1.0–1.33 已完成。1.34 施工文档已写下。号不改。见 [`Ver 1.x/README.md`](Ver%201.x/README.md)。不换一套战斗核心 |
| **2.x** | `new`、`add`。新入口，或已有入口上多一种子结果，包括把已经写好但未激活的旧功能重新用起来。2.1–2.10 已完成，号不改。见 [`Ver 2.x/README.md`](Ver%202.x/README.md) |
| **3.x** | `change`、`change!`。已有结果按新要求改。还没有小版本 |
| **4.x** | `remove!`、`delete!`。去掉子能力，或去掉整个功能、整份资源。还没有小版本 |

类型定义和「同一版必须落在同一段」见 [`../更新日志/README.md`](../更新日志/README.md)。已经收尾的版本号不因为这张表改号。

- **一个小版本 = 一条能独立验收的功能**，按功能切、不按工期切。有硬耦合的东西（没有 A 则 B 测不出对错）捆在同一版，其余各自成版。
- 每个小版本三件套：`游戏设计.md`（做什么、为什么、怎么验收）、`技术设计.md`（改哪些类型、边界在哪）、`TODO.md`（可单独验收的切片，一节一块）。技术设计要点名这一版用的现有入口：角色 Manager、物品动作、伤害碰撞体、敌人 `State.Tick`、Animator 状态、现有 HUD。没有调用方，不新挂 Manager，不新写一套 `State`，不留没有调用方的接口。
- 技术设计里标 **[待确认]** 的接口形状由用户决定，实现时不要自行选一个。
- 小版本完成的标志：TODO 全部勾完、该切片要求的 Edit Mode 测试通过、提交。高风险版本还要 reviewer 结论为「通过」或「有保留通过」。游戏设计写明必须人看的，仍要人看。

## 2. 细化深度

只给**下一个**和**下下个**小版本写全三件套；更远的只写游戏设计或大纲，进入前再补技术设计与 TODO。

技术设计一旦写下类型形状，隔两个版本再看多半要重写。游戏设计（做什么、为什么、验收）过期得慢得多。

提前写出的技术设计 / TODO 若还没进入该版本，文首标「草稿」，进入前对照当时的代码复核后再转正。

## 4. 三条原则

1. **下一刀必须多讲清一个边界。** 改一个看不出来的数字不算进度。这一版结束时，要能说清「谁负责这件事、谁不许碰」。
2. **有使用者才加新类型。** 新的状态、物品动作、伤害入口，要在同一个版本里有实际调用方，不留空接口。
3. **一次只做 TODO 里的一节。** 这一节要能单独验收。不要一次做完整个小版本，也不要顺手做下一版。

## 6. 开工方式

用户点名下一刀之后：

1. 下一刀按日志类型选目录：`fix` 写在 `Docs/开发计划/Ver 0.x/<版本>/`；`refactor` 或 `optimize` 写在 `Docs/开发计划/Ver 1.x/<版本>/`；`new` 或 `add` 写在 `Docs/开发计划/Ver 2.x/<版本>/`；`change` 或 `change!` 写在 `Docs/开发计划/Ver 3.x/<版本>/`；`remove!` 或 `delete!` 写在 `Docs/开发计划/Ver 4.x/<版本>/`。写下三件套，并更新本文件的路线总览。
2. 实现时只做 `TODO.md` 当前那一节。
3. 施工文档一次提交，收尾一次提交。不要按 TODO 的每一节再切一次。提交说明用中文。
4. 高风险版本有代码 diff 时，收尾前由当前 Agent 调用只读的 reviewer。高风险的定义见 [`../版本候选池/README.md`](../版本候选池/README.md)。结论是「要求修改」时改完再审，直到「通过」或「有保留通过」。其余版本不调用。用户点名 `/reviewer` 时仍调用。
