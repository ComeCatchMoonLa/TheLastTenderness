# 更新日志

> **往 [`更新日志.md`](更新日志.md) 追加条目时按本文写。** 0.1–0.35、1.0–1.27、2.1–2.6 已按本文改写过。此后已写下的版本不改条目，更正写进新版本。

版本号仍是两段式 `x.y`。播放器 `bundleVersion` 的 `0.1` 不是这里的版本号。没有补丁号，没有发布日，没有 `Unreleased`：收尾提交时直接写下这一版。

0.x 是纠错，1.x 是行为不变的收拢，2.x 是新增或把已经写好但未激活的旧功能重新用起来。版本段在写施工文档时已经定了。新版本的日志类型必须和这一段一致。对不上时，先改这一版的游戏设计，再写日志。已经收尾的版本号不因为类型表而改号。

## 结构

新的版本在前。版本头是 `## x.y`，下面紧跟条目。

一版通常一条。同一版里玩家能分开感知的结果才拆成多条。多条时按这个顺序排，破坏性的在前：

1. `change!`、`remove!`、`delete!`
2. `new`、`add`、`change`
3. `fix`
4. `optimize`
5. `refactor`

## 条目

```text
- <type>(<模块>)：改了什么；为什么；影响
```

模块用玩家能对上的名字，例如结算、喝药、快捷栏、镜头。类型用英文，模块和正文用中文。

三截都要有：

- **改了什么**：这一版结束时能观察到的结果。
- **为什么**：纠错写原先错在哪；收拢写现在谁负责、谁不再写；新行为写这条结果以前没有。
- **影响**：行为不变就写仍和上一版相同的那一个结果。行为变了就写变前和变后。要改场景、预制体、资产或调用方式时，写迁移。

不用 `update`。

## 类型

类型看玩家能观察到的结果，不看改了多少行。

| type | 定义 | 新版本落在哪一段 |
| --- | --- | --- |
| fix | 行为向本就该有的结果收敛，包括这一版之前从未做对过的。安全修复也归这里 | 0.x |
| new | 新的一层玩家能走到的结果，或把已经写好但未激活的旧功能重新用起来。有单独的入口 | 2.x |
| add | 已有入口上多一种子结果。入口还是原来的 | 2.x |
| change | 已有结果按新要求改了。破坏已有调用、存档或场景时写成 `change!` | 2.x |
| remove | 去掉一个模块里的子能力，模块还在。写成 `remove!` | 按被删的是纠错、收拢还是玩法，落在对应段 |
| delete | 去掉整个功能或整份资源。写成 `delete!` | 同上 |
| refactor | 可观察结果不变，只改谁来写这个结果 | 1.x |
| optimize | 结果不变，只省时间或分配，并且正文里有改前改后的数量 | 1.x。没有数量就写成 refactor |

## 裁决

1. 一条只写一个能单独指认的结果。不要写「多项优化与修复」。
2. 拿不准类型时，先看这一版在开发计划里是 0.x、1.x 还是 2.x，再从该段允许的类型里选。
3. 从来就是错的，写成 fix。以前的结果是当时要求的，现在要求变了，写成 change。
4. 新开一个玩家能单独走到的入口，写成 new。挂在已有入口下，写成 add。
5. 改完之后这个模块还在，写成 remove。整个模块或整份资源没有了，写成 delete。
6. 结果变了的，不写成 optimize。optimize 的正文里没有改前改后的数量时，写成 refactor。
7. 标记以后要删的能力，写成 change。正文写明哪一版去掉，以及现在改走哪一条。
8. 安全修复写成 fix，正文里写明「安全」。

## 示例

- `refactor(结算)：头、躯干、髋的吸收权重只算一次；五段伤害仍各乘这一次；扣血数字与上一版相同`
- `fix(快捷栏)：没有图标时清掉上一张图并停用该格；此前会留下上一件的图；有图标的仍换成新图`
- `add(休息)：休息把三条资源写成上限时，已有回复消耗品的次数写回各自的 maxItemAmount；没休息之前次数不变`
- `add(记忆栏)：格数按集中力门槛可读；以前没有这个格数；9 及以下是 0 格，99 是 10 格，蓝上限仍是等级乘 10`
- `change(装备)!：备用武器计入负重；此前不计入；已有存档按新公式重算`
- `remove(镜头)!：去掉自由镜头的推近；锁定和瞄准仍在；场景里的相机引用改接到剩余两种机位`
- `delete(版本控制)!：卸掉 Unity Collaborate；版本控制只留 Git；不改场景，不改玩法脚本`
- `optimize(锁定)：待机查询复用同一条碰撞体数组；每帧新分配的数组从 1 次降为 0 次；能锁上的目标与上一版相同`

## 原则

- 已经写下的版本不改条目。更正写进新版本。
- `change!`、`remove!`、`delete!` 的影响一截必须写迁移：调用方、场景、预制体或资产改哪一处。
- 一版的日志只记这一版。不把下一版的结果写进来，也不把几版收成一条。
