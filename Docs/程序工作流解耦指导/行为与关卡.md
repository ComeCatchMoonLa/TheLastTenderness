# 行为与关卡

> 叶子行为是代码。顺序、优先级、允许列表和点位是数据。任务、机关和遭遇只排列已经登记的动词。

关卡要改的是「这一下用哪些行为、在哪个点、按什么顺序」，不是再为这一下写一段结算。

## 对方改什么

- 行为的排列：优先顺序、依次执行、从中随机、只执行一次。
- 允许列表：这个场合允许哪些叶子、禁止哪些叶子。
- 点位和区域：刷新点、路径点、触发体积，放在场景里。
- 任务、机关、遭遇：调用闭合动词名单，并填已有参数（旗标、资产 id、点位、数量）。

Damian Isla 在 GDC 2005 关于《Halo 2》AI 的文章里，把关卡设计师写成这套系统的用户：设计师用角色放置、脚本和高层指令排一场戏，而不是每加一条过渡就改一次代码。核心行为图大约有 50 个行为。一条 style 是允许和禁止的行为列表；命令引用 style。优先级不固定时，把「在这种情况下改抢」拆成单独的触发，仍然指向同一个行为，而不是再复制一棵树。

通用决策不够时才写自定义决策。Isla 把两类都留下了：父节点可以用自定义代码做选择，也可以让子节点按相关性竞争。文章里最常用的是优先列表：先试最好的，不行再试下一个，更好的条件出现时可以打断。数量上去之后，用浮点权重硬调出「必须先做 A，除非发生 B」几乎做不到，所以相关性用是否成立，不用一串难以解释的权重。

## 程序留下的合同

动词先登记，再让数据引用。例如：

- 在点位生成
- 设置旗标
- 给予物品
- 发出已登记的声音事件
- 切换一份已登记的允许列表

参数里的 id 必须在进入该内容前解析得到。解析不到就停，报出资产名、动词名和参数名。未知 id 不跳过。

叶子行为是代码：寻路、射击、开门的结算各写一次。数据决定这一场合用不用它、排在谁前面。新的一种叶子才改代码；新的一种组合只改列表或顺序。

```text
优先：玩家在载具中 → 进入载具
然后：战斗
然后：进入载具
```

这是 Isla 把「优先级会变」拆开的示意。触发条件和行为都是已有叶子，不是为这一关写的脚本正文。

自定义决策写完之后，仍由数据选择何时启用。不要在函数里写死某一关的坐标、某一名角色的特例。特例放进允许列表或点位。

## 视觉脚本的边界

the Good Evil 在 GDC 里把目标说成：设计和关卡尽量不改代码就能改内容，手段包括内容管理和视觉脚本。这条目标成立的前提是脚本的能力有边界。

Jon Manning 写 Yarn Spinner 时的约束是：语言只回答一个问题，现在显示哪一句、哪条命令、哪个选项。它不是用来写整个游戏的。结算、存档和战斗公式留在代码里。放进图里之后，调试回到程序身上，而且比代码更难读。

Dan Goodman 2009 年的文章是反例的另一半：工具若只把实现用的原始数据摊开，拼写错误没了，逻辑错误还在，对方仍然要找程序试。关卡资产上应出现的是点位、顺序、允许和禁止，不是一串和私有字段一一对应的裸浮点。引擎里的对象引用、枚举、列表和场景物体已经够用。不要为了这句话先做一套图编辑器。门槛见 [`时间占用.md`](时间占用.md)。

## 空位

点位、允许列表和任务资产可以后到。动词可以先写。

必填点位、必填动词参数、必填行为列表空着时，进入该关卡或该任务前停住，并报出资产名和字段。不要在原点生成一个默认敌人，把「点位还没摆」跑成能玩的结果。可选的支线可以没有，没有就表示这段不启用。

## 做与不做

| 做 | 不做 |
| --- | --- |
| 叶子行为写一次，数据决定顺序和允许 | 每个任务、每个遭遇一份只被它使用的脚本 |
| 刷新和路径用场景里的点位 | 在代码里写死坐标 |
| 未知 id 在进入前拒绝 | 未知 id 跳过，让后面的步骤继续 |
| 视觉脚本或表只调用闭合动词 | 在图里写伤害公式、存档布局或新的结算 |
| 优先级用顺序和是否成立来表达 | 用一长串权重浮点凑出「必须先 A 除非 B」 |

## 何时仍要改代码

- 新的叶子行为，或新的动词。加进名单之后，关卡才能引用。
- 优先列表、顺序、随机、只执行一次都表达不了的决策。写成自定义决策，再由数据打开它。
- 结算规则变了。公式留在叶子里，不拷进某一关的图。

没被当前任务点到的旧行为，不为了改成表或图去重写。
