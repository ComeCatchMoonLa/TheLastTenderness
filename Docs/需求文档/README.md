# 需求文档

> **本文档是《黑暗之魂 3》本体与《艾雷德尔的灰烬》《环印城》的代码相关功能的复刻目标。** 成功时，玩家能亲手走通这些系统里可观察的行为。排期以 [`../开发计划/README.md`](../开发计划/README.md) 为准。

## 阅读顺序

1. 先读调研。目录在 [`../调研文档/README.md`](../调研文档/README.md)。正文按 [`范围.md`](../调研文档/范围.md) 索引的九篇来：角色与养成、装备与建造、移动与镜头、战斗系统、魔法与道具、世界与篝火、界面与场景交互、敌人与头目、角色交互与联机。数值、门槛和次数拿不准时，需求写「与调研中待核对项一致」。
2. 再读 [功能需求/README](功能需求/README.md) 的 FR 索引，按编号进各篇。旧编号是先前窄切片，保留原文；新编号补完整游戏里那一批还没写入的系统。每条标题下标 **当前已有** 或 **待补**，条内含一行 `验收：` 写操作步骤。
3. [`../代码分析/构架设计.md`](../代码分析/构架设计.md) 的「系统入口总览」回答仓库里有没有入口。条目标记以本目录各条标题下的状态为准。对照里的缺口不拿来把已经收尾的条改回待补，也不拿来删掉完整游戏里的系统。
4. [项目目标](项目目标.md)、[非目标](非目标.md)、[验收方式](验收方式.md)（全局验收约定；逐条步骤在各 FR 的 `验收：` 行）。

实现沿用现有结构：`MonoBehaviour`、Animator 的 `StateMachineBehaviour`、`ScriptableObject`。工程编辑器以开发计划为准，记录是 Unity `6000.5.9f1`。本需求不另写引擎版本。

旧编号里的「燃火」指已经写好的窄切片。完整游戏规则里同一处坐下的火写作「篝火」。旧编号不改名、不重排。入口与完整游戏不一致时，新编号写入口；旧编号已经写下的可观察结果（扣魂、加级、休息回满、死亡留魂）仍保留，验收时两条都看。

## 功能需求

全部 FR 的编号索引（已有编号 + 新编号）与条目状态说明在 [功能需求/README](功能需求/README.md)。

调研九篇是 DS3 原作规则。需求可以写调研没有的操作层细化：输入互斥（瞄准中不能跳、冲刺要求未格挡一类）、失败或 0 次时的动作表现（耸肩）、调试开关（`enableAI`）、纯表现反馈（召唤头像、血条隐藏延迟一类）。这些是项目对复刻目标的细化，不按调研冲突登记；只有两边对同一条规则的可观察结论相反（一个说能、一个说不能），才按信息冲突写进 [`../版本候选池/程序功能池/未入池.md`](../版本候选池/程序功能池/未入池.md)。

## 用语

需求与调研对齐时用这些名字：防火女；传火祭祀场；资料片《艾雷德尔的灰烬》《环印城》；催化器是法杖、圣铃、护符、火焰。分瓶在铁匠安德烈。瓶碎片交给铁匠安德烈，总次数加一，血瓶加灰瓶最多十五口。未死人骨片在传火祭祀场主篝火烧掉，每一口的回复升一档，最多加十档。九项属性是生命力、集中力、耐力、体力、力量、敏捷、智力、信仰、幸运。精力上限看耐力，负重上限看体力，蓝条和法术栏看集中力，生命上限看生命力。法术是魔法、奇迹、火焰三系，暗是伤害种类。

## 场景前提

验收在 [验收方式](验收方式.md) 的约定下进行，场景统一如下：

- 已有编号在 Build Settings 里的 `Game` 里看。当前激活内容是玩家、三只近战和 Map 0。燃火条目先只激活已有的 `CampFireInteractable`。
- 雾墙、头目阶段和未激活物体上的脚本，按 FR-机关、FR-头目验收；旧的 FR-敌人仍用当前场景里的三只近战。
- 新编号在能摆出该条角色和交互物的场景里看。关卡怎么铺、哪一面墙是幻影墙，不写进完成条件。
